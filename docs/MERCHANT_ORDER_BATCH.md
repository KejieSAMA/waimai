# 商家订单批量处理（2026-11-14）

## 业务范围

PC、手机商家端仅在对应状态页提供批量处理：新订单可接单／拒单，备餐中可出餐完成，配送中外卖可到达，退款可同意／拒绝。全部、待支付、待自提、已完成、已取消不新增批量动作。

两端先选动作再勾订单；只有一个动作时直接进入选择。已进入平台处理的退款不可选；已经拒绝退款的订单不可再次批量拒绝，但仍沿用现有规则允许商家同意退款。出餐按外卖／自提进入配送中／待自提，到达直接 DONE，用户确认完成不变。

## 接口与事务

- `POST /api/v1/merchant/orders/batch-action` 严格接受 `{ action, ids, reason? }`，action 为 accept／reject／ready／arrive／refund-approve／refund-reject；ids 为 1–100 个不重复、非空且不超过128字符的 ID。
- reason 去除首尾空白，拒单与拒绝退款必填 1–500 字，其他动作可省略。额外字段拒绝，不接受客户端指定店铺归属。
- 返回 `{ results: [{ id, orderNo, outcome, message? }] }`；outcome 为 applied／already_applied／failed，HTTP 200 仅表示已返回逐单结果。失败消息不暴露底层数据库错误。
- 保留六种单笔路径及返回安全订单详情；原 batch-arrive 适配通用服务并保留 completed／already_completed／failed 返回格式。旧共享到达控制仍保留兼容导出，新页面不再使用。

先核验会话和全部订单归属；含其他店铺或不存在的订单时整批404、零写入。之后逐单独立事务，重新核验会话版本、商家授权、首次改密、店铺归属及 OPEN／CLOSED 可写状态；成功项不因其他项失败而回滚。

六种商家单笔与批量共用动作核心，条件更新状态及退款标记，相应时间、库存回补和 merchant-动作 审计同事务完成。只有实际变更提交后才发 updated 静默事件；幂等重放不重写时间、不重复回补、审计或通知。取消类操作须同时有对应 merchant-reject／merchant-refund-approve 审计才能判为已处理，用户取消、平台取消及其他商家动作取消返回冲突；旧无审计取消记录也不推断成功。

同意与拒绝退款的竞争继续受现有规则约束：先同意后不得拒绝；先拒绝后，在用户尚未申诉前仍可合法同意。每个实际生效动作各有一条审计，取消和库存回补只能发生一次。用户申诉成功后商家不可继续处理。用户订单与平台裁定路径不开放商家批量能力。

无数据库迁移，不增加真实支付或退款能力，不修改金额、支付记录及原订单状态机。

## 页面状态

PC 只选当前页，手机只选已加载订单，不跨页隐含全选；每批最多100单。全选仅符合当前动作的已加载数量在1–100时启用，超过上限明确提示分批，不静默截断。PC 当前页默认20单，不增加跨页选择。

切动作、切状态、提交搜索、翻页或退出时清空选择；加载更多不清空。刷新剔除不再符合条件的项。冻结后退出批量并锁定经营动作，保留浏览能力。

提交前确认店铺、操作及数量；拒单／拒绝退款同一确认界面填写统一原因，PC modal、手机 sheet。未提交原因关闭前确认丢弃；提交期间禁止关闭、切换和重复请求。同意退款明确提示所选订单取消。

部分失败保留明细、仍符合动作的失败项及统一原因，重新打开可核对重试。结果区仅显示成功／已处理／失败汇总，失败详情在可滚动 modal／sheet。响应丢失保留确认内容和输入，先只读刷新核对，不自动重发。成功刷新列表、计数、打开详情、店铺状态、统计和角标，保留有效页码与滚动位置；卸载后不应用迟到响应。
